# 18 · Super users and unclaimed organizations (rebuild)

While there are few users, the people running Communalists add organizations themselves so neighbors can find help nearby, such as a church's weekly free shower. These pages are **unclaimed**: nobody owns them, and the real organization can **claim** the page or ask for it to be **taken down**. Agreed with the user on 2026-11-24 ([decision #33](../decisions/033-super-users-and-unclaimed-organizations-claims.md)).

**Status:** built 2026-11-24. **Next:** super users add **events** to unclaimed organizations, once the calendar tool exists. That brings back the prototype's events directory ([03](03-events-directory.md)) with real data.

## Super users

A few accounts ("super users", or platform admins in code) can do what nobody else can. Today that's five things: add unclaimed organizations (one at a time or from a CSV), act as the owner of every unclaimed organization, decide claim requests, download the list of organizations already on Communalists for research (below), and write the dictionary ([19](19-dictionary.md)).

- **Who:** the UIDs in `PLATFORM_ADMIN_UIDS`, comma or space separated, set per environment (Vercel production, and `.env.local`). The list is kept out of the repo. Locally, seeded accounts marked `"platformAdmin": true` are super users too (Jordan Lee; see [getting started](../getting-started.md#test-data)), but only when `isLocalDev()` is true.
- **Removing someone** takes effect on the next deploy (or restart, locally). The list is read on every check, and no session or token holds the role.
- **Checked on the server only:** `isPlatformAdmin(uid)` and `requirePlatformAdmin(next)` in `src/lib/auth/platform-admin.ts`. Every super-user action checks again, because server actions can be called directly.
- **Narrow on purpose.** Super users can't read members-only tool data or act inside claimed organizations. The one exception is public: they moderate reported comments and replies on every listed organization's page ([decision #70](../decisions/070-organization-discussions-platform-moderated-with-official-replies.md)). On unclaimed pages they also write the organization's replies, shown as from the Communalists team. They have no role in an organization unless they're a member of it like anyone else. One stolen super-user account must not expose every group's private data. Add a new power only for a real need, and log it.
- **Photos:** super users can remove any member's photo they can see, or any organization's logo, with a required reason (`removePhoto`, `removeLogo` in `adminLog`, counted under "Photos and logos removed"). [decision #71](../decisions/071-profile-photos-and-organization-logos-cropped-in-browser-firebase-storage.md).
- **Audit:** every super-user action goes in `adminLog`. `/admin` counts them by kind under **Team activity** and lists the decisions (see [Dashboard](#dashboard)).

## Dashboard

`/admin` is the super users' dashboard (rebuilt 2026-11-27, [decision #58](../decisions/058-super-user-dashboard-counts-search-and-missing-details.md)). It used to list every unclaimed organization, which cost 500+ reads after the imports. Top to bottom:

| Section          | What it shows                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Header           | "Numbers as of {time}" (counts are cached up to an hour) and links to each section                                                                                                                                                                                                                                                                                                                                                |
| Needs attention  | How many unclaimed pages have **no way to reach the group**, linking to that list; then the claim requests (below), each with how long it has waited, and an **Over 3 days** label with an icon once it's overdue                                                                                                                                                                                                                 |
| At a glance      | Active organizations (with unclaimed and deleted), the share of team-added pages that have been claimed, organizations added and new accounts in the last 30 days compared with the 30 before, total accounts, and claim requests (with all-time approved and denied). Counts only: no names                                                                                                                                      |
| Trends           | Three small weekly bar charts for the last 12 weeks: new accounts, organizations added, claim requests. Rolling 7-day weeks ending today. The bars are hidden from screen readers; a summary line and **Show as a table** carry the numbers                                                                                                                                                                                       |
| Organizations    | **Add**, **Import from a CSV**, **Download organizations already on Communalists**. **Find an organization**: a GET form (`?q=`, works without scripts) matching the start of the handle or the name, any status, at most 10. **Unclaimed pages missing details**: a filter per gap (`?gap=`) with its count, and the oldest 20 with what's missing and an Edit link. **Recently added**: the 10 newest organizations of any kind |
| Dictionary       | Word count, **Add a word**, **Import words from a CSV**, **Manage the dictionary**                                                                                                                                                                                                                                                                                                                                                |
| Team activity    | Counts for the last 30 days in six groups (added, edited, claims decided, deleted/restored/made unclaimed, words, downloads), then **Decisions and changes**: the latest 20 entries, leaving out adds, edits and downloads, which an import repeats hundreds of times                                                                                                                                                             |
| Recently deleted | As before                                                                                                                                                                                                                                                                                                                                                                                                                         |

**Missing details.** Each organization stores `missingDetails`, worked out on every create and edit (`src/lib/organizations/details.ts`): `phone`, `email`, `website`, `address`, and `contact` when there's no phone, email, website **or** social link. Organizations from before 2026-11-27 need a one-time backfill. In production, press **Fill in missing details** in the missing-details section of `/admin` ([decision #60](../decisions/060-admin-sections-fail-alone-and-backfill-from-the-app.md)). It runs on Vercel with the server's credentials, reads each organization once, writes only the ones that change, logs a `backfillDetails` entry, and refreshes the counts at once. The button disappears after the first run. Locally, `pnpm orgs:backfill-details` does the same against the emulators (dry run; `--write` to save). Its `--production` flag needs Google credentials on your machine, which the button avoids.

**When a read fails** (an index still building, say), only that section says "Couldn't load this section", and the error is in the Vercel logs as `[admin] … failed`. Claims and Recently deleted still fail the page.

**Cost** per cache miss (an hour, or sooner when an action clears the tags): about 30 count reads for the numbers, 36 for the trends, up to 10 for recently added, up to 20 for the missing list, the pending claims, and the 20-entry feed. A search is up to 30 reads (three prefix queries), cached for minutes. Recently deleted reads only organizations archived in the last 30 days.

**Search limits.** Prefixes only, because Firestore has no substring search: "auto club" won't find "Oakland Auto Club", but "oakland auto" will (through the handle). Names are matched as typed and with a capital first letter.

**Visitors** (between Trends and Organizations): numbers from Umami for the last 30 days. Visitors and page views, the most-viewed organizations, and the most-searched cities, each with how many local organizations `/find/organizations` shows there today (under 3 is labeled **Needs research**). Without `UMAMI_API_KEY` it says "Not connected". See [analytics → Reports on /admin](../technical/analytics.md#reports-on-admin) and [decision #59](../decisions/059-umami-reports-on-the-admin-dashboard.md).

**Not yet:** a paginated page of every organization with filters.

## Importing from a CSV

For adding many at once, for example from research on an area ([decisions #40](../decisions/040-bulk-import-unclaimed-organizations-from-csv.md) and [#41](../decisions/041-import-review-edit-remove-explain.md)). `/admin` → **Import from a CSV** opens `/admin/import`.

1. **Review file** reads the CSV in the browser and has the server check every row. **Nothing is added.** Each row goes through the create form's schema with the import's defaults (a handle from the name, US, listed, request to join). Then it's checked for a place ID that doesn't match its `placeLabel`, the same name or handle as an earlier row, a handle already taken, and an active organization with the **same name or website**.
2. **Each row is a card**: ready, or how many things to fix. Each problem names the column (label and CSV name), says what's wrong, shows **what the file says** (for lists, only the wrong entries, like `mutualAid`), and says **how to fix it**. A duplicate links to the organization it matches, with its place and whether it's unclaimed, so you can tell whether it's the same group. **Show profile** opens the real `OrganizationProfile` as the page will look (built from whatever in the row can be read), with the research notes and source links.
3. **Edit** opens the create form in a dialog, filled in from the row: city picker, focus-area boxes, the social links picker and the live handle check. The form's own rules are checked before it closes. Saving re-checks that row against the database. **Remove** takes a row out, with **Undo**. Focus goes back to the row's Edit, or to Undo/Remove, after each step, and each result is announced.
4. **Add N organizations** sits above the list and again below it (not fixed to the screen, so it never covers what has focus). It asks for confirmation, then the server **checks everything again** on fresh data and creates each ready row as an unclaimed organization: one transaction each, with its own `createUnclaimed` entry in the admin log. Added rows leave the review, and the rest stay to fix. The directory cache is cleared so they show in `/find/organizations` right away.
5. **Download CSV** exports the reviewed rows (edits in, removed rows out) in the import format. **Edits live only in the open page**: closing the tab loses them, so download before leaving. That was the user's choice over keeping a draft in the browser.

**Cost:** a database check is up to 4 reads per row (name, website, handle, and the organization holding it). Reviewing a file checks every row. An edit re-checks only that row, and Remove and Undo re-check none (repeats within the file need no reads); the page keeps earlier database findings for the rest (`keepDatabaseProblems`). Adding checks every row again.

**Organizations already on Communalists.** The import page starts with **Download organizations already on Communalists** (`GET /api/admin/organizations`, [decision #43](../decisions/043-find-organizations-skill-and-existing-organizations-export.md)), so research can skip groups that are already here. It's a CSV of every organization: listed, unlisted, unclaimed, and archived (deleted, or taken down at a group's request, which must never be re-added). It has only the organization's own details: name, handle, status, claim status, visibility, place, website, phone, contact email and socials. Nothing about members. Super users only (a plain 404 for anyone else), never cached, one read per organization, and each download goes in the admin log (`exportOrganizations`). Cells starting with `=`, `+`, `-` or `@` get a leading `'`, so a spreadsheet won't run a name someone typed as a formula. The `find-organizations` helpers strip it again. Because it includes unlisted groups, keep the file private: the skill keeps it in `research/`, which git ignores.

Limits: 200 rows, 500 KB, and 5,000 characters per cell. **Finding organizations:** the project skill `.claude/skills/find-organizations/` takes an area, lists its cities, gathers candidates, drops the ones already on Communalists (from the export), in earlier files or rejected before, researches the rest, and checks the file offline with the import's own code (`pnpm orgs:check`). Its sub-agents run on smaller models (Haiku to gather candidates, Sonnet to research), and groups it couldn't check go in a `pending.txt` that later runs retry ([decision #45](../decisions/045-find-organizations-sub-agent-models-and-pending-list.md)). **Preparing a file:** the project skill `.claude/skills/prepare-organizations-csv/` describes every column and the research rules: leave a cell blank rather than guess, organizations' public details only, a source for every row. It also has a template and `find-place.mjs` to look up place IDs. Code: `src/lib/organizations/import.ts` (reading the file with the shared `src/lib/csv.ts`, row checks, previews, CSV export, form conversion; tested), `import-store.ts` (database checks and the import), `existing.ts` (the export's format and the skill's matching; tested) and `export-store.ts`.

## Making an organization unclaimed

For a super user who added an organization the normal way by mistake, and so is listed as its owner ([decision #37](../decisions/037-deleting-organizations-restore-and-make-unclaimed.md)). **Make unclaimed** appears in the members' space when they're a super user, an owner, and its only active member. After a confirmation, their membership and any join requests are removed, and it becomes unclaimed with the same handle and details. It's refused when anyone else is a member, because they'd silently lose their group. Logged in the admin log.

Verified 2026-11-24: as Jordan, created Mistake Pantry without ticking unclaimed, so he was listed as Owner. **Make unclaimed** turned it into an unclaimed page, with its phone, year and address unchanged.

## Claiming or taking down

The notice has **Is this your organization? Claim it**, which goes to `/organization/{handle}/claim` (sign-in and a finished account needed).

1. **The request:** what they want (**Manage this page** or **Take this page down**), their role there (up to 100 characters), and how the team can confirm it's them (10 to 1,000 characters, for example "call the church office and ask for me"). The form says that only the team sees it, together with their name and account email, and that we may email them about it.
2. **Review:** super users see pending requests on `/admin`, oldest first, with the role, the note, a link to the person's profile, and their **account email** (read from Firebase Auth when the page loads, never stored with the request). The page tells them to check outside the app before approving, for example by phoning the organization's public number. There's no automatic proof: a domain-email check would leave out the many small groups that use Gmail.
3. **Decision**, checked again on fresh data in one transaction (`decideClaim`):
   - **Approve a claim:** the person becomes the **owner**. The organization stops being unclaimed and super users lose their access to it. Its log says "{name} claimed this organization". The 5-owned limit applies.
   - **Approve a takedown:** the organization is **archived**, like an owner deleting it: the page and listings disappear and the handle stays reserved.
   - **Deny:** the request is marked denied. They see "We couldn't confirm your last request" and can send a new one.
   - Approving closes everyone else's pending request for that organization (`outcome: resolvedByOther`).
4. **The person sees** their request's status on the claim page (sent on {date}, with **Cancel request**). Once approved, the organization is on their dashboard. **No notifications yet:** there's no email sending, so the team emails them by hand if needed.

## Data

- `organizations/{id}`: `claimStatus: 'unclaimed'` while unclaimed (removed when claimed), `memberCount: 0`, `createdBy` (the super user). After a claim: `claimedBy`, `claimedAt`. Every organization: `missingDetails[]` ([Dashboard](#dashboard)).
- `claimRequests/{orgId}_{uid}`: `intent` (`claim`/`remove`), `role`, `message`, `status` (`pending`/`approved`/`denied`), `outcome` (`decided`/`resolvedByOther`), `org { name, handle }` and `claimant { displayName, username }` (copies), `requestedAt`, `decidedAt`, `decidedBy`. One per person per organization; a new request after a denial replaces it.
- `adminLog/{id}`: `action` (`createUnclaimed`, `editUnclaimed`, `approveClaim`, `approveRemoval`, `denyClaim`, `removePhoto`, `removeLogo`, and others listed in `AdminAction`), `orgId`, `orgName`, `actorUid`, `target { uid, displayName }?`, `fields[]?`, `reason?`, `createdAt`. Append-only.
- In an organization's `moderationLog`: `claim` entries, and `actor { uid, team: true }` for super-user edits.

All through the Admin SDK; the rules still deny clients. Queries: `claimRequests where status == pending`, `claimRequests where orgId == X and status == pending`, and the dashboard's counts and lists (`src/lib/organizations/stats-store.ts`). The dashboard's `adminLog where action in [...]` (counted since a date, or ordered by date) and the missing-details queries need the composite indexes in `firestore.indexes.json`; everything else is equality-only or one range or order. Reads are cached and tagged (`claims`, `adminLog`, `directory`); the actions that write clear them.

## Privacy

A claim collects a role and a free-text note, and shows the account email to super users. Nothing else is collected, and none of it is ever public or logged. Requests aren't deleted after a decision, so a disputed claim can be looked into later. If that turns out not to be needed, delete decided requests after a while.
