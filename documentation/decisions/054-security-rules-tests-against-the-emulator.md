# 054 · Security rules tests against the Firestore emulator, in CI

**Date:** 2026-11-26
**Status:** Accepted
**Context:** `AGENTS.md` asks for security rules "with tests", and issue #140 asked for rules tests for the dictionary, but the repo had no way to test rules. The rules deny every client and all access goes through the Admin SDK, so the tests would only prove that. The user chose to add the setup now, so each collection opened later reuses it.
**Decision:** `@firebase/rules-unit-testing` with Vitest, in `rules/` with its own config (`vitest.rules.config.mts`, Node environment), kept out of `pnpm test` because it needs the emulator. `pnpm test:rules` starts the Firestore emulator with `firebase emulators:exec` and runs them; with `pnpm dev` already running, `pnpm exec vitest run --config vitest.rules.config.mts` uses its emulator. The tests check that signed-out and signed-in clients can't read, write, delete or list every collection we store, plus the dictionary's planned comments and votes. They write nothing, so a running dev emulator keeps its data. CI installs Java 21 (`actions/setup-java`) and runs `pnpm test:rules` after the unit tests. Checked by loading allow-all rules once: all 72 tests failed.
**Alternatives:** deferring until a collection opens to clients (the deny-all rules would stay untested, and the first opening would also have to build the setup); running rules tests inside `pnpm test` (it would need the emulator for every unit test run).
**Consequences:** A new dev dependency and a slower CI (the emulator starts in a few seconds; Java is installed each run). A new collection should be added to the test's list. The Realtime Database rules aren't tested (it's unused, and not in the emulator config). Docs updated: [tooling and CI](../technical/tooling-and-ci.md), [firebase](../technical/firebase.md), `AGENTS.md`.
