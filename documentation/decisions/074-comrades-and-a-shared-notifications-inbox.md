# 074 · Comrades, and a shared notifications inbox

**Date:** 2026-11-28
**Status:** Accepted, built the same day
**Context:** The user wanted a comrades feature, like friends: one person sends a request and the other accepts it on their dashboard. Comrades show on profiles, like endorsements ([decision #73](073-endorsements-on-profiles-count-on-organization-pages.md)). Becoming comrades should open up a private profile, and more comrade-only features may follow. The user also asked for a notification system that comrade requests use first, and that organizations will use later: posting events, asking members for things, library checkouts.
**Decision** (each point the user's choice from options we laid out; the first option was recommended each time):

- **Comrades see your details at every visibility level.** The levels keep their stored keys and get new labels: Everyone / My groups and comrades (`groups`) / Only my comrades (`name`, was "Just my name"). With no comrades, "Only my comrades" still shows just the name. Group privacy is unchanged: a comrade sees only the groups they could already see. This applies wherever a person's details or photo show: profiles, member lists, the members page, comments, notifications.
- **Who can send requests is a setting:** Anyone signed in (default) / People in my groups / Nobody. **Declining is silent:** the sender keeps seeing "Request sent", and can't ask the same person again for 30 days. A sender can have at most **50 requests waiting**. No "Add comrade" button shows when the person's setting wouldn't take a request from you.
- **A comrades list on profiles respects both people's privacy:** it follows the owner's visibility and a "Show my comrades" switch (on by default), and each comrade is listed only if their own visibility would show this viewer their details. A profile shows six with "See all comrades" (`/comrade/{username}/comrades`).
- **Notifications are a general, in-app inbox:** a bell in the header with an unread count (on every screen size), `/notifications` for all of them, and a "Comrade requests" card on the dashboard with Accept and Decline. Each notification has a `kind`; the first are `comradeRequest` and `comradeAccepted`. No email and no live updates yet: the count updates when a page loads.
- **Removing a comrade asks first and is silent.** Like sharing with fewer people ([decision #71](071-profile-photos-and-organization-logos-cropped-in-browser-firebase-storage.md)), both people's photos move to a new link unless their profile is public.

**Alternatives:** a fourth visibility level just for comrades (more choice, one more option to explain); comrades counting as groupmates only (wouldn't open a "Just my name" profile); requests open to anyone with no setting, or a setting defaulting to groups only; a comrades list filtered by the owner's privacy only, or a count only; notifications only on the dashboard until a second kind exists, or only in the inbox.
**Consequences:** New server-only collections `comradeships/{low}_{high}` (one per pair, sorted uids; pending, accepted or declined) and `notifications/{kind}~{ref}~{uid}`, both in the deny-all rules tests. Notifications are listed by `uid` ordered by `createdAt`, a **composite index** in `firestore.indexes.json`: deploy it before merging. Every change runs in one transaction with its notifications, and an answered or taken-back request's notification is deleted. `profile.comrades { show, requests }` in user settings, and a `comrade` viewer in `src/lib/profiles.ts`. Comrades are read with `uids array-contains` and cached per person, so a profile with many comrades costs one read per comrade on a cache miss (each comrade's profile is cached too). New analytics events `comrade-request`, `comrade-cancel`, `comrade-accept`, `comrade-decline`, `comrade-remove`, `comrade-sign-in` (where only, never who). The Vietnamese and Chinese words ("bạn đồng hành", "伙伴") avoid the political sense of "đồng chí" and "同志" and are open to review.
