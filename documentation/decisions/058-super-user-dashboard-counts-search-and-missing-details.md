# 058 · Super-user dashboard: counts, search, and missing details

**Date:** 2026-11-27
**Status:** Accepted
**Context:** `/admin` listed every unclaimed organization (500+ after the Bay Area imports), so each cache miss cost 500+ reads, and the list wasn't useful at that size. It also read the whole dictionary to show one number, and Recently deleted read every organization ever archived. The user asked for a dashboard with useful information, actionable insights, the data-entry tools in one place, and analytics on claims, team actions and new users.
**Decision:** (the user picked each recommended option)

- **Numbers come from `count()` aggregation queries**, which Firestore bills at one read per 1,000 matching documents. About 30 counts for the numbers and 36 for the 12-week trends, each cached for up to an hour and cleared by the same tags as the data (`directory`, `claims`, `adminLog`). Rolling windows (last 7 and 30 days, compared with the 30 before), not calendar weeks, so no time zone is involved.
- **Search plus recently added replaces the full list.** Search is by handle prefix (the typed text turned into a handle) and name prefix (as typed and capitalized), at most 10 results. Recently added is the 10 newest organizations of any kind. A paginated browse page can come later.
- **A derived `missingDetails` field on every organization** (`contact`, `phone`, `email`, `website`, `address`; `contact` means no phone, email, website or social link), written on create and edit, with a one-time backfill script. The dashboard counts the gaps in active unclaimed pages and lists the oldest 20 for the chosen gap, with Edit links.
- **Trends as numbers plus three small weekly bar charts** (new accounts, organizations added, claim requests): one series each, no shared axis, with a summary line and a table for screen readers.
- **Team activity: counts for every action, a list for decisions only.** An import writes hundreds of `createUnclaimed` entries, which would push every decision off a plain log. So adding, editing and downloads are counted (six groups, one `action in [...]` count each), and the feed lists claim decisions, deletes and restores, and dictionary changes.
- **Umami reports (top organizations, searched cities, cities with few results) were deferred** until there was an API key, then built the same day ([decision #59](059-umami-reports-on-the-admin-dashboard.md)).

**Alternatives:** paginating the full list (still not useful at 500); a daily summary document written by a scheduled job (one read per view, but more moving parts and up to a day stale); counting gaps by reading every unclaimed page (the cost we're removing); showing new users by name (not needed for the insight, and it's personal data); per-super-user counts (needs another index, and the team is small).
**Consequences:** Four composite indexes are now in `firestore.indexes.json` and must be deployed (`firebase deploy --only firestore:indexes --project communalists`) before the dashboard works in production. The backfill (`pnpm orgs:backfill-details --production --write`) must run once. It writes around the app, so counts can stay stale for up to an hour after it, until something clears the tags. Every new write path for organizations must set `missingDetails` (only `newOrganizationFields`, `updateOrganization` and the seed write details today).
