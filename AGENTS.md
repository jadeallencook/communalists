# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## Project

Communalists is a **platform for mutual aid networks**: anyone can sign up, create or join **organizations** (e.g. "South Bay Mutual Aid", "Oakland Auto Club"), and run them with **tools** built for mutual aid (requests + kanban, a lending library, calendars, documents…). Each tool can have a public side and a members-only side, and each organization gets a public page at `{slug}.communalists.com`. It's like Facebook Groups, with purpose-built tools instead of a feed. The UI is in English, Spanish, Vietnamese and Chinese. Read `documentation/product-vision.md` first.

Two earlier codebases came first: a React + Webpack + Firebase prototype (2022–2024, commit `7ebc168`) and a Next.js + Prismic marketing shell (2025, commit `81eed51`). Both were removed, and the repo now starts from these docs. The rebuild uses **Next.js (App Router) + Firebase + Tailwind/shadcn/ui, hosted on Vercel, with locale routing (`en`, `es`, `vi`, `zh`) from day one**. See decisions #3–#8 in `documentation/decisions/` (`003-…` to `008-…`). What both attempts taught is kept in `documentation/`.

## Working methodology

The prototype was for discovery, and so is the rebuild. We expect to change direction, reverse earlier calls, and try things the prototype never did. The docs make that safe: each new choice is made knowing what came before and why.

**Keeping the docs current is a core part of the work, not a cleanup step afterward.** A change isn't done until the docs match it.

1. **Read first.** Before working on a feature, read its doc and any technical doc it touches (table below). Start from what we already learned.
2. **Push back and ask.** The user doesn't expect to know everything and wants to hear it when you do. If you know a better approach, see a risk in what was asked, or would build it differently with more context, say so or ask before building. Questions and objections are welcome, not an inconvenience, whenever they lead to a more stable product, a better user experience, or clearer wording. Give a recommendation and the reason, not just a list of options. Once the user decides, build what they chose and log it (rule 6). This applies to code, UX and copy alike, and it outranks "just do what was asked." (Set by the user 2026-11-21.)
3. **Treat docs as guidance, not law.** The prototype's choices are a starting point. If the user picks a different direction, follow the user and update the docs to match. Don't argue for the old design just because it's written down, but do point out anything in the docs that suggests the new direction could repeat a known mistake (rule 2).
4. **Update in the same change.** When a feature, data shape, rule, dependency or decision changes, edit the matching doc in the same commit or PR. Don't leave a doc describing behavior that no longer exists.
5. **Write down what you learn.** If you hit a non-obvious constraint, a bug's root cause, a library quirk, a cost or performance finding, or a user preference about how the product should work, add it to the relevant doc. If nothing fits, create a new one. If it would have saved you time, it belongs in the docs.
6. **Log decisions.** Every meaningful choice gets its own file in `documentation/decisions/`, named `NNN-what-it-is-about.md` so it can be found with `ls` or `grep`: what we chose, what we considered, and why. See `documentation/decisions/README.md` for the template and index. That covers picking a framework, dropping a feature, changing the data model, or going against something in these docs.
7. **Keep history, don't erase it.** When the rebuild replaces a prototype behavior, rewrite the doc to describe the **current** behavior. Keep the old approach in a short "Prototype" note when the lesson still matters. Delete only what is truly obsolete.
8. **Fix stale docs on sight.** If you notice a doc that's wrong, outdated, or missing a link, fix it now, even if it isn't part of your task. Mention it in your summary.
9. **Say what you changed.** At the end of a task, list the docs you created or updated, or say plainly that none needed changes.

Docs describe _what_ and _why_. Leave the line-by-line _how_ to the code, and don't duplicate it there.

## Components and Storybook

Two rules for all UI work (set by the user 2026-11-21, decision #13):

1. **No business logic in presentational components.** They take props and render, nothing else: no data fetching, server actions, sessions, Firebase, or validation rules. Logic lives in `src/lib/` (domain code with no React or Next imports, so a future React Native app can reuse it), `src/hooks/` (shared UI logic), and thin **containers** in `src/app/` that fetch data, wire actions, and render a page. Pass server actions in as props (`formAction`, `signOutAction`); never import them into `src/components/`. If an action changes something shown outside its own form (like the name in the header), call `refresh()` from `next/cache`.
2. **Every new page or component gets a story**, in one of these Storybook categories (the sidebar enforces the order):

| Storybook title          | Folder                        | What goes there                                                            |
| ------------------------ | ----------------------------- | -------------------------------------------------------------------------- |
| `Documentation/…`        | `documentation/`, `AGENTS.md` | Generated from the `.md` files; never write these stories by hand          |
| `Components/Atoms/…`     | `src/components/atoms/`       | Smallest building blocks: the shadcn primitives (`shadcn add` writes here) |
| `Components/Molecules/…` | `src/components/molecules/`   | A few atoms with one job: `FeatureCard`, `LocaleSwitcher`                  |
| `Components/Organisms/…` | `src/components/organisms/`   | Page sections: `SiteHeader`, `HeroBanner`, `SignUpForm`                    |
| `Pages/…`                | `src/components/pages/`       | Whole-page views. Routes render them with real data; stories use mocks     |
| `Hooks/…`                | `src/hooks/`                  | A demo component showing the hook's states, with mocked dependencies       |

Story conventions: put `Name.stories.tsx` next to the component, cover the important states (empty, error, loading, long text), use `parameters: { layout: 'fullscreen' }` for full-width pieces, and use `fn()` from `storybook/test` for actions. Components must be synchronous (use `useTranslations`, not `await getTranslations`), because Storybook can't render async Server Components.

## Current product rules

These are the rules we're building to today. They can change. When one does, update it here, update the feature doc, and log it in `documentation/decisions/`.

- **Accessibility is the top priority** (set by the user 2026-11-23). Many people using the platform may have a disability, and it must work for everyone. WCAG 2.2 AA is the floor: keyboard-only use with visible focus, meaningful names for screen readers, announced results and errors, sensible focus after actions, contrast in both themes, 200% zoom, reduced motion, plain language. Every change meets `documentation/technical/accessibility.md` before it's done, and its summary says what was checked.

- **Multi-tenant:** every piece of tool data belongs to exactly one organization. Scope every query, rule and server check by organization and by the user's membership role.
- **Open sign-up, gated data:** anyone can create an account and an organization. Being signed in grants nothing inside an organization; membership and role do.
- **Public vs internal:** each tool declares what is public (anyone, signed out included) and what is members-only. Default to members-only.
- **Languages:** `en`, `es`, `vi`, `zh` for the UI. Organization content (names, pages, items) is written by users and isn't translated. A form's language field should default to the visitor's UI language.
- **Access checks run on the server or in security rules, never only in the UI.**
- **Usable accounts:** every signed-in page's container calls `requireAccount(next)` (`src/lib/auth/require-account.ts`). It sends signed-out visitors to sign-in, and accounts missing a required answer (`src/lib/account-setup.ts`) to `/account/setup`. New required questions go in that list, not in sign-up.
- **Privacy:** tools like Requests collect names, phone numbers, addresses and health conditions. Never expose them publicly, never log them, and collect no personal fields without a clear use. The prototype removed unused fields on purpose (`documentation/features/14-removed-experiments.md`).
- **Super users** (`PLATFORM_ADMIN_UIDS`) add **unclaimed organizations** and act as their owners until a group claims one; claims are reviewed by a super user. Keep their powers narrow: no access to members-only data in claimed organizations, and every action goes in `adminLog` (`documentation/features/18-unclaimed-organizations.md`).
- **Shared devices:** clear any cached organization data on sign-out.
- **Requests tool** (from the prototype): pipeline `submitted` → `started` → `ready` → `complete`, plus `cancelled`; oldest first; intake can be paused without a deploy, and it fails closed.

## Engineering conventions

- TypeScript in strict mode. Validate every form and every server input with a shared schema.
- Don't bump `package.json` `version`; nothing shows it. The footer shows the commit each build came from, so it's always clear which build is live (decision #46).
- Commits follow **Conventional Commits** (`feat:`, `fix:`, `chore(scope):`), enforced by commitlint.
- Format with Prettier: 4 spaces, single quotes, semicolons, ES5 trailing commas.
- CI must check lockfile drift, formatting, types, lint, tests and build. Keep the lockfile committed and pin Node in `.nvmrc`.
- Define path aliases once, in `tsconfig.json`.
- **Firestore reads go through a cached, tagged function** (`'use cache'` + `cacheTag` + `cacheLife`), and the action that writes clears the tag (`updateTag`). Decide access on fresh data, show cached data. Call `logRead()` beside every read. See `documentation/technical/firebase.md` → "Caching reads in the rebuild".
- Write tests for date and time logic (event open/closed in `America/Los_Angeles`), filtering and phone formatting. These were the buggy areas before.
- Keep security rules or database policies, and indexes, in the repo, with tests.

## Git

- **Don't commit or push unless asked.** By default, leave every change uncommitted in the working tree; the user reviews, commits and pushes. Switching branches is fine, but never discard uncommitted work to do it.
- **When someone asks for a pull request**, follow `.claude/skills/prepare-pull-request/SKILL.md` (decision #44): new branch, checks, commit, push, `gh pr create`. That request covers that PR only, never merging or force-pushing.
- When a task is done, summarize what is ready to commit (files and a suggested Conventional Commit message).
- `main` is protected (decision #42): changes land through a squash-merged pull request with a code owner's approval and green CI. The PR title becomes the commit message, so suggest one that passes commitlint.

## Don't

- Don't use hash routing or a client-only SPA for public pages. They need real, crawlable, locale-prefixed URLs.
- Don't hard-code content organizers need to edit (services or events, FAQ). Keep it in a DB or CMS.
- Don't duplicate the request and donation stacks. Model them as one case entity with a `type`.
- Don't commit secrets. Firebase web config is public, but service-account keys and env files are not.
